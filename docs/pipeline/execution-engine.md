# 실행 엔진

파이프라인 한 번의 실행(run)이 어떻게 흘러가는지, 그리고 **왜 그렇게 흐르는지**를 정한다. 여기
적힌 규칙 대부분은 "이렇게 안 하면 데이터가 조용히 유실된다"는 종류다.

## 실행 모델 — 타깃 주도 풀(pull) 스트리밍

```
1. 트리거(cron / 수동)
      ▼
2. 백엔드가 DAG 검증 → run 레코드 생성 → 큐에 enqueue
      ▼
3. 워커가 위상 정렬 → 타깃마다 상류를 거슬러 제너레이터 체인 구성
      ▼
4. 타깃이 배치를 당겨온다(pull). 당겨진 만큼만 소스가 읽힌다.
      ▼
5. 노드 상태·진행률 갱신 → WebSocket으로 화면에 push
      ▼
6. 모든 타깃 성공 → 워터마크 전진 → run 완료
```

**푸시(push)가 아니라 풀(pull)인 이유**: 소스가 읽는 대로 밀어내면 타깃이 느릴 때 중간 결과가
메모리에 쌓인다. 타깃이 당겨오게 하면 **가장 느린 타깃의 속도로 전체가 흐르고, 메모리에 쌓이는
것은 배치 하나뿐이다.** 프로덕션 DB에서 수천만 행을 읽는 상황에서 이 차이는 결정적이다.

구현상으로는 각 노드가 `AsyncIterable<RecordBatch>`를 반환하고, 타깃 노드의 `for await`가 체인
전체를 구동한다.

## 노드별 실행은 미리보기다 — 쓰기 경로가 아니다

캔버스의 "선택 노드만 실행"([canvas-ux.md](canvas-ux.md))은 위 run 흐름과 **다른 것**이다. 둘을
헷갈리면 run 단위로 걸어둔 보호 장치가 통째로 비껴간다.

- **소스·변환 노드에만 적용된다.** 타깃 노드는 단독 실행할 수 **없다.**
- 앞의 소스·변환 체인을 **샘플 몇 배치만** 흘려보고 결과를 화면에 보여준다. 어떤 타깃에도 쓰지
  않으며, 스풀 파일도 남기지 않는다.
- **워터마크를 전진시키지 않는다.** 미리보기 때문에 다음 실행이 데이터를 건너뛰면 안 된다.
- run 레코드(`pipeline_runs`)를 만들지 않는다. 실행 이력에 섞이면 "이 파이프라인이 언제 돌았나"가
  흐려진다.
- 소스에 실제 쿼리를 날리므로 **감사 로그에는 남는다.** 프로덕션 DB를 읽는 모든 경로가 남는다는
  원칙에는 예외가 없다 ([audit-logging.md](../policy/audit-logging.md)).

> **타깃에 쓰는 진입 경로는 run 단위 실행 하나뿐이다.** cron·수동·재시도 셋 다 같은 잠금과 같은
> 감사 기록을 통과한다([pipeline-write-boundary.md](../policy/pipeline-write-boundary.md) 규칙 7).
> 미리보기에 쓰기를 허용하면 그 경로가 둘이 되고, 둘이 되는 순간 한쪽이 빠진다.

## 워터마크 (증분 적재)

증분 적재는 "지난번에 어디까지 읽었나"를 기억하는 것이다. 그 값이 워터마크다.

### 규칙 1 — 모든 타깃이 성공한 뒤에만 전진한다

```
타깃 A 성공, 타깃 B 실패  →  워터마크 전진 ✗ (그대로 둔다)
타깃 A 성공, 타깃 B 성공  →  워터마크 전진 ✓
```

미리 올리면 실패한 구간이 **영구히 유실된다.** 다음 실행이 이미 올라간 워터마크부터 읽기 때문에
그 구간을 다시는 보지 않는다. 재실행해도 복구되지 않는다는 점이 이 규칙을 하드 룰로 만든다.

### 규칙 2 — 타입 태그를 붙여 저장한다

워터마크 값이 timestamp나 numeric이면 **타입 정보를 함께 저장한다.**

```json
{ "column": "updated_at", "type": "timestamptz", "value": "2026-08-06T01:23:45.678Z" }
```

값만 저장하면 다음 실행에서 문자열로 되살아나 `updated_at > '2026-08-06...'` 비교가 **조용히**
어긋난다. 에러가 나면 차라리 낫다 — 이 실패는 아무 소리 없이 잘못된 행 집합을 가져온다.

JSON은 timestamp도 Decimal도 모른다. 태그를 붙이는 건 선택이 아니다.

### 규칙 3 — 전체 적재(full refresh)는 워터마크를 무시한다

수동 실행에 `fullRefresh: true`를 주면 워터마크 조건 없이 전량을 읽는다. 성공하면 워터마크는
**이번 실행의 최대값으로 갱신된다**(초기화가 아니다).

## 쓰기 모드와 overwrite 규칙

| 모드 | 동작 | 멱등성 |
|---|---|---|
| `append` | 그냥 추가 | ✗ — 재실행 시 중복. 로그성 데이터에만 |
| `upsert` | 키 충돌 시 갱신 | ✓ — **기본으로 권장** |
| `overwrite` | 기존 데이터를 치우고 적재 | ✓ — 단 아래 규칙 필수 |

### overwrite는 저장소 종류에 따라 다르게 동작한다

**DB 타깃**: **첫 배치에서만** 테이블을 비운다.

배치마다 비우면 마지막 배치만 남는다. "왜 100만 행 중 5천 행만 들어왔나"의 전형적인 원인이다.
엔진이 첫 배치 여부를 알려주고, 커넥터는 그때만 truncate 한다.

**S3 · 파일 타깃**: **`run_id=` prefix 아래에 쓰고, 그 prefix를 선정리한다.**

```
s3://bucket/exports/orders/run_id=1042/part-0000.jsonl
                                      /part-0001.jsonl
```

실행마다 경로가 분리되므로 **실패한 실행이 성공한 실행의 결과를 오염시키지 않는다.** 같은 실행을
재시도하면 그 prefix만 지우고 다시 쓰면 되므로 멱등하다. 공용 경로에 덮어쓰면 중간에 실패했을 때
"반쯤 지워진 데이터"가 남는다.

## 팬아웃 — 소스를 정확히 한 번만 읽는다

한 소스가 두 타깃으로 갈라지면(분기), 순진하게 구현하면 **소스를 두 번 읽는다.** 프로덕션 DB에
같은 무거운 쿼리를 두 번 날리는 셈이다.

그래서 분기 지점에서는 **스풀(JSONL 임시 파일)** 로 받는다.

```
source ──▶ [스풀 파일 write] ──┬──▶ 타깃 A (스풀 read)
                              └──▶ 타깃 B (스풀 read)
```

- 소스는 **한 번만** 읽힌다.
- 타깃은 **순차 실행**한다. 동시에 돌리면 스풀을 두 번 읽는 이득이 사라지지 않지만, 타깃 쪽
  부하가 겹치고 실패 처리가 복잡해진다.
- 스풀 파일은 run 종료 시 **성공·실패와 무관하게 정리**한다.
- 스풀은 격리된 임시 디렉터리 아래에만 만든다. 경로를 사용자 입력으로 조립하지 않는다.

분기가 없는 파이프라인은 스풀을 만들지 않는다. 스풀은 팬아웃이 있을 때만 켜지는 최적화다.

## 실패와 재시작

| 단위 | 처리 |
|---|---|
| 배치 | 커넥터 레벨 재시도 (지수 백오프, 상한 있음) |
| 노드 | 노드 단위 재시도. 재시도 횟수 소진 시 run 실패 |
| run | 체크포인트(워터마크)부터 재시작 |

- **재시도해도 소용없는 에러는 즉시 실패시킨다.** 인증 실패, 존재하지 않는 테이블, 권한 없음은
  백오프해도 똑같다. 재시도 대상 에러를 화이트리스트로 좁힌다.
- `close()`는 실패 경로에서도 반드시 호출한다.
- 부분 성공한 실행의 상태는 `node_states`에 노드별로 남긴다. "어디까지 됐나"를 화면에서 볼 수
  있어야 재시작이 무섭지 않다.

## 같은 파이프라인의 동시 실행을 막는다

**원본 청사진이 "스케줄러에는 있으나 수동 실행 경로에는 아직 없다"고 남긴 구멍이다. DITTER는
처음부터 양쪽 모두에 건다.**

같은 파이프라인이 겹쳐 돌면:

- 워터마크가 서로를 덮어쓴다.
- `overwrite` 타깃에서 한쪽이 다른 쪽이 쓰는 중인 테이블을 비운다.

**Redis 잠금을 파이프라인 ID로 건다.** cron 트리거·수동 실행·재시도 **모든 진입 경로**가 같은
잠금을 통과한다. 잠금이 잡혀 있으면 새 실행은 큐에 넣지 않고 즉시 "이미 실행 중"으로 거절한다.
잠금에는 TTL을 두고 실행 중 갱신한다(워커가 죽어도 영원히 잠기지 않게).

## 진행률과 실시간 push

- 진행률·처리 행수처럼 **초당 여러 번 바뀌는 값은 Redis에 두고 WebSocket으로 화면에 push**한다.
- SQLite에는 **노드 상태가 바뀔 때만** 기록한다. 진행률을 매번 SQLite에 쓰면 잠금 경합이 난다
  ([README.md의 메타 저장 주의](README.md#️-메타-저장을-sqlite로-두는-것의-한계)).
- WebSocket은 헤더를 붙일 수 없어 토큰을 쿼리스트링으로 받는다. 그래서 **이 토큰의 수명은 짧게**
  둔다 — 쿼리스트링은 프록시·접근 로그에 남는다.

## 워커 운영

BullMQ 기준. 원본 청사진의 Celery 권고를 옮긴 것이며, 근거는 동일하다.

| 설정 | 값 | 왜 |
|---|---|---|
| `concurrency` | **명시한다** (기본 2) | 미지정 시 과도하게 동시 실행 → 메모리 압박 + SQLite 잠금 경합 |
| `lockDuration` | 배치 처리 시간보다 넉넉히 | 짧으면 정상 실행 중인 잡이 stalled로 오인돼 중복 실행된다 |
| `maxStalledCount` | 1 | 워커가 죽으면 한 번만 재개. 무한 재개는 같은 실패를 반복한다 |
| 큐 분리 | 무거운 커넥터는 별도 큐 | 큰 적재 하나가 가벼운 잡을 굶기지 않게 |
| 컨테이너 mem/CPU limit | **건다** | 없으면 워커 하나가 호스트를 잡아먹는다 |

- **잡은 멱등해야 한다.** 워커가 죽어 재개될 때 같은 잡이 다시 실행될 수 있다. 위 overwrite
  규칙과 upsert 기본값이 이 전제를 지탱한다.
- 워커는 **무상태**다. 상태는 Redis(잠금·진행률)와 SQLite(이력·체크포인트)에만 있다. 워커를
  아무 때나 죽이고 다시 띄울 수 있어야 한다.

## 감사 로그와의 관계

파이프라인 실행도 **프로덕션 DB에 쿼리를 날린다.** 따라서 감사 로그에서 빠지면 안 된다
([audit-logging.md](../policy/audit-logging.md)).

- 소스 읽기는 **run 단위로 한 건** 남긴다. 배치마다 남기면 감사 로그가 파이프라인 로그에 파묻힌다.
- 타깃 쓰기는 **별도 기록**한다 — 어느 커넥션에 어떤 모드로 몇 행을 썼는지. 쓰기는 콘솔에서
  불가능한 동작이므로 더 자세히 남긴다 ([pipeline-write-boundary.md](../policy/pipeline-write-boundary.md)).
- **run에 속하지 않는 두 경로도 한 건씩 남는다** — 노드 미리보기(누를 때마다, 읽은 커넥션마다)와
  워터마크 수동 되돌리기. 컬럼별 채움 규칙은 [audit-logs.md](../schema/audit-logs.md)에 있다.
- 실행 상세 로그(`pipeline_run_logs`)는 감사 로그가 **아니다.** 용도가 다르고 보존 정책도 다르다.
