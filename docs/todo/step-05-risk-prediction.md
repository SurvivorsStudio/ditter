# STEP 5 · 🚩 실행 전 위험 예측 (`F3` 완성 · 킬러 기능)

**시작 조건**: STEP 4

## 목표

**이 제품의 심장이다.** 사용자가 실행 버튼을 누르기 전에, 도구가 먼저 EXPLAIN을 떠서 "이 쿼리는 1000만 행짜리 테이블을 전부 훑습니다. 실행하면 서비스가 느려질 수 있습니다"라고 붙잡는다.

**여기서 데모 시나리오가 처음부터 끝까지 관통된다.** 조회 시도 → 위험 경고 → AI 대안 → 안전한 실행. 이 흐름이 끊기지 않고 한 번 돌아가는지 반드시 확인하고 넘어간다.

## 정직하게 범위를 좁혀야 한다

실행 전 EXPLAIN으로 알 수 있는 것(큰 테이블 풀스캔, 예상 비용·행수 급증, 인덱스 미사용 조인)과 없는 것(락 경합, 리플리카 지연 등 런타임 동시성 현상)이 명확히 갈린다. 표와 상세 근거는 [query-safety-limits.md](../policy/query-safety-limits.md) 참고. 이걸 예측한다고 홍보하면 심사에서 찔린다. 대신 STEP 7의 **실시간 관찰** 기능으로 다룬다.

## 하는 일

- 실행 전 EXPLAIN을 떠서 위험 신호 탐지: 대용량 Seq Scan, 예상 비용/행수 급증, 인덱스 미사용 조인
- 위험하면 경고 + 사람 말로 된 이유 설명 + 더 가벼운 대안 제시
- **회귀 테스트 세트**: 대표 쿼리를 고정해 두고 판정 결과를 매번 검증
- **데모용 시드 데이터**: 느린 쿼리가 실제로 재현되는 대용량 테이블

## ⚠️ 시드 데이터를 절대 뒤로 미루지 마라

가장 자주 후순위로 밀렸다가 데모 당일에 터지는 항목이다. **데이터가 없으면 위험 예측도 튜닝도 시연할 수 없다.** 그냥 못 보여준다.

Seq Scan이 "실제로 느리게" 보이려면 수백만~천만 행이 필요하다. 컨테이너 기동 시간과 이미지 크기에 영향을 준다. 매번 같은 실행 계획, 같은 지연이 나오도록 **재현성을 고정**해야 한다. 생성 스크립트 + 사전 ANALYZE(통계 갱신) + 시드 고정까지가 범위다. **STEP 2~3 진행 중에 미리 준비할 것.**

## 통계 신선도 주의

EXPLAIN의 예상 행수는 DB 통계에 의존한다. 통계가 낡으면 추정이 크게 틀린다. **마지막 ANALYZE 시각을 함께 노출**해서 사용자가 판단할 수 있게 하라.

## 완료 조건 🚩

① 고정된 대표 쿼리 세트에서 위험/안전 판정이 매번 동일하게 재현되고, 오탐·미탐이 합의된 허용선 안에 든다.
② **데모 시나리오가 처음부터 끝까지 한 번 관통된다.** (조회 시도 → 위험 경고 → AI 대안 → 안전한 실행)

> 🚩 **여기가 하드 게이트다.** ②가 안 되면 다음으로 진행하지 않는다. 뒤 STEP들은 이 관통 위에 얹히는 것이지, 이걸 대신해 주지 않는다.
>
> 규칙을 넓게 벌리면 오탐이 늘어 신뢰를 잃는다. **소수의 명확한 규칙으로 좁게 시작하는 게 낫다.**
