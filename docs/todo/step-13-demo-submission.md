## 완료 조건 🚩

리허설에서 시나리오가 끊김 없이 재현된다.

## 경쟁 지형 참고

"EXPLAIN 해석 + 인덱스 추천 + 슬로우 쿼리"는 이미 붐비는 영역이다. pganalyze(자동 인덱스 어드바이저), pgMustard·explain.dalibo(EXPLAIN 시각화), EverSQL, Postgres.ai(DB 브랜칭 + 실측 튜닝)가 이미 있다.

DBeaver + ChatGPT만 경쟁자로 상정하면 심사에서 곧장 찔린다. 우리가 실제로 방어할 수 있는 차별점은 개별 기능이 아니라 다섯 가지의 결합이다.

1. 프로덕션의 실제 상태를 읽어 근거로 삼음
2. 읽기 전용이라 안전하게 붙일 수 있음
3. 셀프호스팅 오픈소스 (데이터가 외부로 안 나감)
4. 에디터 · AI · 관찰이 한 화면에 통합
5. **그 안전한 쿼리를 그대로 반복 적재(파이프라인)로 만들 수 있음** — 여기서 비교 대상이 아예
   바뀐다. pganalyze류는 데이터를 옮기지 않고, Airbyte·Fivetran류는 쿼리 위험을 예측하지 않는다.
   **"위험 판정을 통과한 쿼리만 파이프라인 소스가 된다"는 조합은 어느 쪽에도 없다.**

발표 자료에 **기존 도구 비교표**를 반드시 넣어라.

## ⚠️ 반드시 나올 질문: "읽기 전용이라며 왜 쓰기가 있나"

F7이 붙는 순간 심사에서 거의 확실히 나온다. 얼버무리면 2번 차별점이 통째로 무너진다. 준비된
답은 [pipeline-write-boundary.md](../policy/pipeline-write-boundary.md)에 있고, 요지는 이렇다.

> **사람에게 열어주는 SQL 실행 경로는 여전히 읽기 전용 하나뿐입니다.** 타깃 쓰기는 사람도 AI도
> SQL을 넣을 수 없는 별도 경로이고, 실행 가능한 문장이 세 가지로 유한하며, 전용 계정·전용
> 스키마에서만 일어나고, 전부 감사 로그에 남습니다. 콘솔 계정에는 여전히 **읽는 권한만** 주면
> 됩니다.

**콘솔 계정 권한은 표로 말한다.** "읽기 전용 계정 하나면 끝"이라고 뭉뚱그렸다가 F5 시연에서
`pg_read_all_stats`를 더 요구하면 이 답변 전체의 신뢰가 흔들린다. 발표 자료에는
[P3의 권한 표](../policy/read-only-enforcement.md#콘솔-계정에-정확히-무엇을-주는가)를 그대로
싣는다 — 추가되는 롤도 읽기 권한이라는 점이 오히려 주장을 강하게 만든다.

말로만 하지 말고 **데모에서 보여줘라** — 콘솔 접속 목록에 타깃 커넥션이 없다는 것, 타깃
커넥션으로 쿼리를 실행하면 거부된다는 것 두 장면이면 충분하다.
