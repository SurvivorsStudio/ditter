# 이기종 쿼리 엔진 경계 (P10)

F1 콘솔에 확장이 하나 붙는다 — **서로 다른 엔진(PostgreSQL + MySQL)에 등록된 읽기 전용 소스
커넥션 여러 개를, 하나의 쿼리로 조인해 결과를 보여준다.** 사내에서 흔히 겪는 "주문은 Postgres에,
고객은 MySQL에 있다"는 상황을 위한 기능이다.

이것도 P9와 같은 이유로 경계를 먼저 못 박고 시작한다 — **여러 프로덕션 DB에 동시에 닿는 새
경로**라서, 흐릿하게 두면 "읽기 전용이라 안전하다"는 주장이 가장 먼저 흔들리는 지점이다.

## 결론부터

> **이 기능이 다루는 것은 `role='source'` 커넥션뿐이다. `role='target'`에는 어떤 경로로도 닿지
> 않는다. 결과는 화면에 보여주는 것으로 끝나며, 새로운 저장 경로를 만들지 않는다.**

| | 콘솔 단일 소스 (F1) | 이기종 쿼리엔진 |
|---|---|---|
| 다루는 커넥션 | `role='source'` 하나 | `role='source'` 여러 개(엔진 혼합 가능) |
| `role='target'` 접근 | 불가 | **불가 (동일)** |
| 각 소스에 도달하는 문장 | AST 검증 통과 후 실행 | **엔진마다 AST 검증 통과 후 실행 (동일, 완화 없음)** |
| 결과의 최종 위치 | 화면 그리드 | 화면 그리드 (**새 저장 경로 없음**) |

## 규칙 1 — 다루는 것은 `role='source'`뿐이다

콘솔의 커넥션 선택과 같은 라우터 앞단 가드를 그대로 탄다 ([P9 규칙 2](pipeline-write-boundary.md#규칙-2--타깃-커넥션은-콘솔에서-도달할-수-없다)).
차이는 `adapter_type`이 `postgres` 하나가 아니라 `postgres` · `mysql` 여러 개를 섞어 고를 수
있다는 것뿐이다. `role='target'`은 이 선택지에 **한 번도** 나타나지 않는다.

## 규칙 2 — 각 소스 접근은 콘솔과 완전히 같은 방어를 탄다

파이프라인 소스 읽기가 예외를 두지 않는 것과 같다 ([P9 규칙 8](pipeline-write-boundary.md#규칙-8--소스-읽기는-콘솔과-완전히-같은-방어를-탄다)).

- 각 소스는 **읽기 전용 DB 계정**(주방어)으로만 접근한다.
- 사용자가 입력하는 것은 "이 조인을 표현하는 쿼리 텍스트" 하나이지만, 최종적으로 **각 소스에
  도달하는 부분 문장은 그 엔진의 AST 검증을 통과해야 한다.** `sqlglot`으로 PostgreSQL·MySQL
  양쪽 방언을 하나의 라이브러리로 검증한다 — [1B](../todo/step-01b-readonly-validator.md)의 검증기를
  엔진별로 재사용한다.
- 각 소스에 `statement_timeout`(또는 MySQL의 `MAX_EXECUTION_TIME`)과 풀 상한을 그대로 건다
  ([query-safety-limits.md](query-safety-limits.md)).
- **자체 접속을 열지 않는다.** 어떤 엔진(DuckDB/Polars)을 쓰든, 각 소스로의 실제 연결은 DITTER의
  커넥션 레지스트리에 등록된 `role='source'` 커넥션의 자격증명만 쓴다. 사용자가 호스트·자격증명을
  직접 입력해 즉석에서 붙는 경로는 만들지 않는다 — 파이프라인 커넥터가 자체 접속을 안 여는 것과
  같은 이유다 ([connector-contract.md](../pipeline/connector-contract.md)).

## 규칙 3 — 결과는 트랜지언트다. 새 쓰기 경로를 만들지 않는다

결과는 콘솔 결과 그리드에 표시되는 것으로 끝난다. 이 기능은 **새로운 영구 저장 테이블이나 새로운
쓰기 경로를 만들지 않는다** — 그러면 P9가 막으려는 것과 같은 종류의 위험(쓰기 경로 확산)이
다시 열린다.

이건 [F7 파이프라인의 "조인 노드는 범위 밖"](../pipeline/dag-and-nodes.md#여러-상류가-한-노드로-모이면)
결정과 **다른 얘기다.** F7은 반복 배치 적재이고, 이 기능은 1회성 대화형 조회다. 이 기능이 있다고
F7에 조인 노드를 넣어야 한다는 요구로 이어지지 않는다 — 필요하면 여전히 "소스 쿼리에서 SQL로
조인해서 읽는다"가 답이며, 이기종 조인이 필요하면 콘솔에서 먼저 확인한 뒤 각 엔진의 소스를
그대로 F7에 등록한다.

## 규칙 4 — 리소스 상한

인메모리 엔진(DuckDB/Polars 중 무엇이든)에 여러 소스의 결과를 올려 조인하는 연산은, DB 하나에
쿼리 하나를 날리는 콘솔의 기본 동작보다 자원을 더 쓴다.

- **조인 이전에 각 소스에서 가져오는 행 수 상한**을 둔다. 콘솔의 `max_rows`([connections.md](../schema/connections.md))를
  그대로 쓰거나 이보다 낮게 잡는다 — 조인 전에 이미 크기를 줄여야 인메모리 단계의 OOM을 막는다.
- **전체 연산(모든 소스 읽기 + 조인)의 총 시간 상한**을 소스별 `statement_timeout`과 별도로 둔다.
- **동시에 조인할 수 있는 소스 수를 MVP에서는 낮게 제한한다**(2~3개). 소스가 늘수록 조인 비용은
  조합적으로 커진다.

## 규칙 5 — 감사 로그

F7의 "노드 미리보기"와 같은 패턴을 재사용한다 ([pipeline-write-boundary.md 규칙 7](pipeline-write-boundary.md#규칙-7--쓰기는-전부-감사-로그에-남는다)).

- 실행마다 **관련된 소스 커넥션 각각에 한 건씩** 감사 로그를 남긴다.
- 여러 건이 "하나의 이기종 조회"였음을 나중에 묶어 볼 수 있도록 **공통 식별자**(예: `federated_query_id`)를
  같이 남긴다. 컬럼 추가는 [audit-logs.md](../schema/audit-logs.md)에서 다룬다.

## 엔진 선택 — DuckDB vs Polars (팀 결정 필요)

어느 엔진을 쓰든 위 규칙 1~5는 동일하게 적용된다 — 엔진 선택은 "조인 연산을 무엇으로 구현하는가"
이지 "누가 방어선을 지키는가"를 바꾸지 않는다. 트레이드오프는 다음과 같다.

| | DuckDB | Polars |
|---|---|---|
| 조인 표현 | `postgres_scanner`/`mysql_scanner` 확장으로 각 소스에 **직접 attach**하고 표준 SQL 한 줄로 조인 | 각 소스에서 결과를 먼저 추출해 DataFrame으로 만든 뒤 `.join()` API 호출 |
| 사용자 학습 비용 | 낮다 — 콘솔에서 쓰던 SQL 문법 그대로 | 있다 — SQL이 아닌 조인 API를 새로 노출하거나, 콘솔 위에 SQL→호출 변환 계층이 필요 |
| 커넥션 통제 지점 | DuckDB 확장이 소스에 자체적으로 연결한다 — **규칙 2의 "자체 접속 금지"를 지키려면 DITTER가 발급한 자격증명을 이 확장에 그대로 넘기는 통합 지점이 필요** | DITTER 어댑터가 추출까지 전담하므로 커넥션 통제가 상대적으로 단순 |
| 각 소스 AST 검증 시점 | attach 뒤 엔진에 넘기는 SQL 전체를 검증해야 하며, DuckDB가 내부적으로 어떻게 부분 쿼리를 각 소스로 밀어내는지(pushdown)까지 감안해야 정확하다 | DITTER가 각 소스에 실제로 보내는 쿼리를 직접 조립하므로 검증 지점이 명확하다 |
| 의존성 | DuckDB 코어 + 확장 두 개 | Polars + 소스별 추출 라이브러리(connectorx 등) |

**팀이 먼저 정할 것**은 [todo README](../todo/README.md#팀이-먼저-결정해야-할-것)에 있다.
