# 파이프라인 쓰기 경계 (P9)

**DITTER는 읽기 전용이다**([P3](read-only-enforcement.md)). 그런데
[파이프라인 기능(F7)](../pipeline/README.md)은 목적 저장소에 **쓴다.** 이 문서는 그 모순을 어떻게
해소하는지 정한다.

이건 정책 문서 중 가장 먼저 읽어야 할 축에 든다. 여기가 흐릿하면 "읽기 전용이라 안전하다"는
제품의 핵심 주장이 무너진다.

## 결론부터

> **읽기 전용 강제는 하나도 완화되지 않는다. 쓰기는 완전히 분리된 두 번째 경로에서만 일어나며,
> 그 경로에는 사람도 AI도 자유형 SQL을 넣을 수 없다.**

| | 콘솔 (F1~F6) | 파이프라인 소스 | 파이프라인 타깃 |
|---|---|---|---|
| 자유형 SQL | 허용 (읽기만) | 허용 (읽기만) | **불가** |
| AI 생성 SQL | 허용 (검증 후) | 허용 (검증 후) | **불가** |
| DB 계정 권한 | 읽기 전용 | 읽기 전용 | 쓰기 허용 |
| AST 검증 | 필수 | 필수 | 해당 없음 |
| 화면에서 도달 가능 | ✓ | ✓ | 타깃 노드로만 |

## 규칙 1 — 커넥션은 역할이 나뉘고, 겸할 수 없다

`connections` 테이블에 `role` 컬럼을 둔다 ([connections.md](../schema/connections.md)).

| `role` | 용도 | DB 계정 권한 |
|---|---|---|
| `source` | 콘솔 조회 · 파이프라인 소스 | **읽기 전용** (`default_transaction_read_only = on`) |
| `target` | 파이프라인 타깃 **전용** | 지정 스키마에 한정된 쓰기 |

**한 커넥션이 두 역할을 겸할 수 없다.** 겸하게 두면 콘솔에서 쓰기 권한 계정으로 쿼리를 날릴 수
있게 되고, 그 순간 P3의 주방어(DB 계정 권한)가 사라진다. 같은 DB에 소스와 타깃 양쪽으로 붙어야
한다면 **계정을 두 개 만들어 커넥션을 두 개 등록한다.**

## 규칙 2 — 타깃 커넥션은 콘솔에서 도달할 수 없다

- 쿼리 실행 API는 `role='target'` 커넥션을 **거부한다.** 요청이 어디서 왔든, 권한이 무엇이든.
- 접속 선택 UI는 타깃 커넥션을 콘솔 화면에 **아예 노출하지 않는다.**
- 스키마 조회 · EXPLAIN · 운영 관찰(F5)도 마찬가지로 타깃 커넥션에 붙지 않는다.

이 거부는 **라우터 앞단 한 곳**에서 강제한다. 각 핸들러가 알아서 검사하게 두면 새 엔드포인트가
추가될 때 빠진다.

## 규칙 3 — 쓰기는 자유형 SQL이 아니다

타깃에 나가는 문장은 **커넥터의 `write()`가 생성하는 것뿐이다**
([connector-contract.md](../pipeline/connector-contract.md)).

- 허용 동작은 `append` · `upsert` · `overwrite` **세 가지뿐이다.**
- 대상 테이블·컬럼은 파이프라인 정의에서 오고, **식별자는 화이트리스트 검증 후 인용(quote)**
  한다. 문자열 이어붙이기로 테이블명을 넣지 않는다 ([P1](internal-vs-user-query-injection.md)).
- 값은 **전부 파라미터 바인딩**이다.
- **사용자나 AI가 입력한 텍스트가 타깃 DB의 문장으로 흘러가는 경로는 존재하지 않는다.**

즉 타깃에서 실행될 수 있는 SQL의 형태는 **유한하고 우리가 다 알고 있다.** 이건 콘솔의 상황(임의
SQL을 받아 검증)과 근본적으로 다르며, 그래서 타깃 쪽에는 AST 검증기가 필요 없다.

## 규칙 4 — AI는 타깃에 대해 아무것도 만들지 않는다

AI(F2·F3·F4)의 작용 범위는 **소스 쿼리까지**다.

- AI에게 타깃 커넥션의 자격증명·호스트를 컨텍스트로 주지 않는다.
- AI가 적재 모드나 대상 테이블을 **바꾸도록 제안하는 기능을 만들지 않는다.**
- 파이프라인 정의를 AI가 생성하는 기능은 MVP 범위 밖이다. 넣게 되더라도 **저장 전 사람 확인이
  필수**이며, 저장 시점에 규칙 1·2·5의 검증을 전부 통과해야 한다.

## 규칙 5 — 타깃 DB 계정 권한을 최소로 준다

주방어는 여기서도 **DB 계정 권한**이다. 앱 코드의 검증은 보조다.

권장 권한:

```sql
-- 지정 스키마에만, 지정 테이블에만
GRANT USAGE ON SCHEMA ditter_load TO ditter_writer;
GRANT SELECT, INSERT, UPDATE, DELETE, TRUNCATE ON <대상 테이블들> TO ditter_writer;
```

**주지 않는 것**:

- `DROP` — `overwrite`는 `TRUNCATE`로 충분하다. `DROP` 권한이 있으면 버그 하나가 테이블을 날린다.
- DDL 일반(`CREATE` · `ALTER`) — 대상 테이블은 **사람이 미리 만든다.** 파이프라인이 테이블을
  자동 생성하지 않는다.
- 대상 스키마 밖의 어떤 권한도.
- superuser · `pg_write_all_data` 같은 광역 롤.

문서에 이 권한 목록을 그대로 실어 두는 이유는, 도입하는 회사가 **"이 도구에 무슨 권한을 줘야
하나"에 복사해서 답할 수 있게** 하기 위해서다. P3의 "읽기 전용 계정만 주면 된다"와 같은 성격의
문장이다.

## 규칙 6 — 타깃 커넥션 등록은 더 엄격하다

- 타깃 커넥션 등록·수정은 **관리자만** 한다 ([P6](authentication-authorization.md),
  [connection_grants](../schema/connection-grants.md)).
- 이미 `source`로 등록된 **같은 host·port·database**를 타깃으로 등록하려는 경우, 화면에서
  명시적으로 한 번 더 확인받는다. "프로덕션을 읽으려다 프로덕션에 쓰게 되는" 사고의 대부분이
  이 지점에서 난다.
- 자격증명 저장·암호화는 기존 [P4](credential-management.md)를 그대로 따른다. 파이프라인용으로
  새 암호화 메커니즘을 만들지 않는다.

## 규칙 7 — 쓰기는 전부 감사 로그에 남는다

[P7 감사 로그](audit-logging.md)의 연장이다. 쓰기는 콘솔에서 불가능한 동작이므로 **읽기보다 더
자세히** 남긴다.

| 남기는 것 | 이유 |
|---|---|
| 누가 실행을 트리거했나 (수동/스케줄) | 스케줄 실행도 등록한 사람이 있다 |
| 어느 타깃 커넥션에 | |
| 어느 테이블·경로에 | |
| 어떤 모드로 (`append`/`upsert`/`overwrite`) | `overwrite`는 파괴적이다 |
| 몇 행이 쓰였나 | |
| 파이프라인 ID + **실행 시점 버전** | 정의가 그 뒤 바뀌었을 수 있다 |

- 소스 읽기는 **run 단위로 한 건** 남긴다(배치마다 남기면 감사 로그가 파묻힌다).
- 파이프라인 실행 상세 로그(`pipeline_run_logs`)는 **감사 로그가 아니다.** 용도도 보존 정책도
  다르며, 감사 로그의 append-only·삭제 불가 원칙을 대신할 수 없다.

## 규칙 8 — 소스 읽기는 콘솔과 완전히 같은 방어를 탄다

파이프라인이라고 예외를 두지 않는다.

- 읽기 전용 DB 계정 (주방어)
- AST 기반 문장 검증 — `ReadSpec`의 `query`도 검증기를 통과해야 한다. CTE 안의 DML, `pg_sleep`,
  `SECURITY DEFINER` 함수, `FOR UPDATE` 전부 동일하게 막는다.
- `statement_timeout` · 풀 상한 ([P5](query-safety-limits.md))
- **행 수 상한은 배치 단위로 적용한다.** 콘솔의 `max_rows`(응답 한 번에 담기는 행 수 상한)는
  파이프라인 소스 읽기에 걸지 않는다 — 스트리밍이라 응답이라는 단위가 없고, 여기에 걸면 대량
  적재가 조용히 잘린 채 성공으로 끝난다. 파이프라인 쪽에서 메모리를 지키는 것은 **한 배치의 크기
  상한**이며, 전체 소요 시간은 `statement_timeout`이 막는다
  ([connections](../schema/connections.md)의 `max_rows`).

**소스 커넥터는 자체 접속을 열지 않고 STEP 1의 DB 어댑터를 경유한다.** 위 방어가 전부 그 어댑터에
붙어 있기 때문이다. 다만 어댑터가 콘솔용으로 거는 `max_rows`는 파이프라인 경로에서 배치 크기
상한으로 대체된다 — **파이프라인 전용 최대 행수는 두지 않는다.**

## 리뷰 게이트

🔒 **규칙 1·2·3의 구현은 2인 리뷰 필수 대상이다.** [P3](read-only-enforcement.md)·
[P4](credential-management.md)와 같은 등급으로 취급한다. 이 셋 중 하나라도 뚫리면 읽기 전용
콘솔이 쓰기 가능한 콘솔이 된다.

[STEP 12 보안 전수 점검](../todo/step-12-security-review.md)에서 다음을 **실제 코드로** 확인한다.

- [ ] 쿼리 실행 API가 `role='target'` 커넥션을 거부한다 (테스트로 고정)
- [ ] 타깃 커넥션이 콘솔 접속 목록 API 응답에 포함되지 않는다
- [ ] 타깃에 나가는 문장이 커넥터가 생성한 세 가지 형태뿐이다
- [ ] 식별자가 화이트리스트 + 인용을 거친다
- [ ] AI 컨텍스트에 타깃 커넥션 정보가 들어가지 않는다
- [ ] 쓰기가 감사 로그에 위 항목 전부와 함께 남는다

## 심사에서 "읽기 전용이라며 왜 쓰냐"고 물으면

준비된 답이 있어야 한다.

> **DITTER가 사람에게 열어주는 SQL 실행 경로는 여전히 읽기 전용 하나뿐입니다.** 파이프라인 타깃
> 쓰기는 사람이 SQL을 넣을 수 없는 별도 경로이고, 실행 가능한 문장이 세 가지로 유한하며, 전용
> 계정·전용 스키마에서만 일어나고, 전부 감사 로그에 남습니다. 콘솔 계정에는 여전히 읽기 권한만
> 주면 됩니다.
