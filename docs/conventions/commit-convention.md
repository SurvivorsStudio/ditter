# Git 커밋 규칙 (COMMIT Convention)

## 커밋 단위

- 변경은 **논리적으로 독립된 최소 단위**로 나누어 **커밋마다 하나의 목적**만 담는다. 여러 작업을 한 커밋에 **통합하지 않는다**("한 번에 올리기" 지양).
- **PR vs 커밋**: **feature 브랜치·리뷰 단계**에서는 한 PR에 커밋이 **여러 개** 있어도 되고(영역·목적별로 쪼갠다), **리뷰는 커밋 단위**로 본다. 단 **main 반영은 squash 머지**이므로 **main 히스토리에는 PR당 한 커밋**만 남는다 — 아래 「[머지 정책 (main 반영)](#머지-정책-main-반영)」 참조.

### 1차 분할(필수): 영역 — `frontend/` · `backend/` · `worker/` · `packages/` · `docs/`

- **한 커밋에는 아래 중 하나의 영역만** 포함한다. 경로가 **둘 이상**이면 **커밋을 나눈다**.
  - **`frontend/`** — 프런트엔드 앱 (React + Vite 웹 콘솔 + 파이프라인 캔버스, TypeScript)
  - **`backend/`** — 백엔드 앱 (FastAPI, Python — DB 어댑터, AI 컨텍스트 빌더, 위험 판정 등)
  - **`worker/`** — Celery 워커 (파이프라인 DAG 실행, Python) — [STEP 9](../todo/step-09-pipeline-foundation.md)에서 생긴다
  - **`packages/`** — 백엔드·워커가 공유하는 Python 패키지 — DAG 스펙(`dag-spec`), 커넥터 라이브러리(`pipeline-connectors`) ([project-structure.md](project-structure.md) 참고). 프런트엔드와의 타입 공유는 OpenAPI 코드 생성으로 하므로 이 영역에 들어가지 않는다
  - **`docs/`** — 개발 계획(`todo/`)·보안 정책(`policy/`)·컨벤션(`conventions/`)·스키마(`schema/`)·파이프라인 설계(`pipeline/`) 문서
- **의도**: 되돌리기·리뷰·히스토리 탐색 시 "어느 층을 건드렸는지"가 커밋 단위로 바로 드러나게 한다.
- **구현과 문서를 같은 과제로 묶는 경우에도**, **파일 경로 기준으로 커밋은 분리**한다(예: 위험 판정 로직 구현은 `backend/` 커밋, 완료 조건·정책 문구 갱신은 `docs/` 커밋). **한 PR**에 순서대로 올리면 된다.
- **`packages/`의 공유 타입(DAG 스펙 등)을 바꾸면서 이를 쓰는 `frontend/`·`backend/`·`worker/` 코드도 함께 고쳐야 하는 경우**에도, 타입 변경(`packages/`)과 소비 측 변경은 분리하고 **타입 커밋을 먼저** 올린다.

### 2차 분할: 영역 안에서 최소 단위

각 영역(`frontend/` · `backend/` · `worker/` · `packages/` · `docs/`) **내부**에서만 아래를 적용한다.

- **쪼개는 기준(예시)**
  - **같은 영역 안에서** 서로 다른 **타입**이면 분리한다(예: `backend/`에서 `feat` 구현과 `test`만 추가가 섞이면 분리할지 판단 — 동일 버그 수정에 필수 테스트는 아래 예외 참고).
  - 서로 다른 **모듈·주제**(예: `backend/`의 DB 어댑터 vs 위험 판정 규칙)에서 **무관한** 변경이면 분리한다.
  - **리팩터·포맷**과 **동작 변경**이 섞이면 분리한다(리뷰·되돌리기 단위를 위해).
  - 서로 다른 **STEP·기능(F1~F7)**을 한 커밋에 넣지 않는다.

### 커밋 분리 — 문서(`docs/`)만 다룰 때

- **서로 다른 과제**이면 **무조건 분리**한다. 예:
  - `docs/todo/step-05-risk-prediction.md`의 완료 조건을 고치는 커밋 vs `docs/policy/read-only-enforcement.md`의 문구를 고치는 커밋.
- `docs/`만 바꾸는 경우에도 **파일·주제가 다르면** 커밋을 나눈다(예: `docs/todo/` 특정 STEP 수정 vs `docs/conventions/` 용어 수정).

### 저장소 루트·그 외 경로 (다섯 영역 밖)

- **위 다섯 영역에 속하지 않는 경로**(예: `.github/`, 최상위 `docker-compose.yml`, CI 설정, 인프라 스크립트)만 변경하는 경우에는 **그 목적 하나**에 맞춰 **별도 커밋**으로 둔다.
- **한 변경이 루트 설정과 특정 영역을 동시에** 건드리면(예: 공용 설정 + `backend/` 코드), **영역별 커밋으로 쪼갠다**(루트/공용 한 커밋 + 해당 영역 한 커밋). 가능하면 **영역 커밋**이 설정 변경에 의존하도록 **커밋 순서**를 맞춘다.

### 커밋 분리 — 반대로 묶어도 되는 경우

- 동일 버그 수정에 **필수인 테스트**만 추가한 경우.
- 동일 기능을 깨뜨리지 않으려면 함께 가야 하는 **불가분한** 소수 파일(팀이 합의한 범위).
- 위는 **예외**이며, "한 번에 올리기 편해서" 묶는 것은 허용하지 않는다.
- 위 예외도 **다섯 영역의 경로를 한 커밋에 섞지 않는** 범위에서만 적용한다.

### 안티 패턴(지양)

- **`frontend/`**, **`backend/`**, **`worker/`**, **`packages/`**, **`docs/`** 중 **둘 이상의 영역** 경로를 한 커밋에 넣는다(1차 분할 위반).
- 서로 무관한 **기능 구현 + 다른 STEP의 문서**를 한 커밋에 넣는다(영역을 나눠도 각 커밋은 하나의 목적만).
- 포맷·정리 전체와 **기능 변경**을 한 커밋에 넣는다(리뷰·bisect가 어려워진다).

## 머지 정책 (main 반영)

- **main 은 팀 전체가 공유하는 브랜치**다. main 에 **직접 push 하지 않고**, 항상 feature 브랜치에서 작업해 **PR 로 반영**한다. 브랜치 이름엔 **항상 prefix** 가 붙는다 — `feature/`, `bug/`, `fix/` 만 사용하며 prefix 없는 맨 이름은 만들지 않는다.
- **머지 전략은 squash 고정**이다. PR 의 여러 커밋은 main 으로 머지될 때 **하나의 커밋으로 합쳐진다**. 따라서 **main 히스토리는 PR당 한 커밋**이며, `revert`·`bisect`·히스토리 탐색의 단위는 main 에서 **PR(= squash 커밋)** 이 된다.
- 위 「커밋 단위」의 영역·목적별 분할 규칙은 여전히 **feature 브랜치 안에서 그대로 적용**한다 — 리뷰어가 PR 안에서 변경을 의미 단위로 따라갈 수 있어야 하기 때문이다. squash 로 합쳐지더라도 **개발 중 커밋을 대충 뭉치지 않는다**.
- **squash 커밋 메시지**도 아래 「커밋 메시지 포맷」을 따른다. 제목은 PR 제목, 본문은 PR 변경 요약·관련 이슈/맥락(있으면)을 `-` 글머리로 정리한다.
- 머지 후 feature 브랜치(원격·로컬)는 삭제한다.

> 원격은 **GitHub**([SurvivorsStudio/ditter](https://github.com/SurvivorsStudio/ditter))이므로 PR 생성·머지는 `gh pr create`·`gh pr merge --squash`로 한다. 커밋을 영역별로 쪼개 스테이징·커밋하는 작업은 `commit` 스킬이 이 정책대로 처리한다.

## 커밋 메시지 포맷
- 한 줄은 100자 (한글 50자) 이하로 작성한다.
```text
<타입>: <제목>
<빈줄>
<본문>
```

## <타입> 작성 방법
아래 타입만 사용한다.

- `fix` : 버그 수정
- `feat` : 새로운 기능 추가
- `docs` : 문서 수정 (예: README.md 등)
- `build` : 빌드 시스템 또는 종속성 변경
- `refactor` : 코드 리팩터링 (동작에 영향 없는 코드 개선, 포맷팅, 주석 수정 등)
- `test` : 테스트 코드 추가 또는 수정
- `chore` : 기타 작업 (간단한 소스 변경, UI/CSS 수정, 파일/폴더 이동·삭제 등)

- **scope 괄호는 쓰지 않는다.** 제목은 `<타입>: <제목>` 형식이며, `fix(risk):`·`feat(explain):` 처럼 타입 뒤에 `(...)` 를 붙이지 않는다(예: `fix(risk): 오탐 수정` ✗ → `fix: 위험 판정 오탐 수정` ✓). 영역 구분은 위 「[커밋 단위](#커밋-단위)」의 영역별 분리로 표현하고, 대상은 제목 본문에 자연어로 적는다.

## <제목> 작성 방법
1. 제목은 **50자 이내**로 작성한다.
2. 제목은 **현재형**, **명령문 형태**로 작성한다.

## <본문> 작성 방법
1. 제목에서 설명이 완벽하면 본문은 선택사항이다.
2. 변경 이유와 내용을 명확히 작성한다.
3. 본문은 글머리 기호(`-`)를 사용해 작성한다.
